# Release Notes Board

A small full-stack board for drafting, reviewing, and publishing application release notes. It consists of an Angular single-page UI, a Spring Boot REST API, and PostgreSQL persistence.

## Included

- List applications and release-note entries.
- Create an entry assigned to an application (new entries begin as `DRAFT`).
- Change an entry between `DRAFT`, `REVIEW`, and `PUBLISHED`.
- Server-side request validation and consistent JSON errors.
- PostgreSQL schema and seed applications managed by Flyway.
- Backend integration tests using H2 in PostgreSQL compatibility mode.
- Dockerfiles and a Docker Compose setup for the complete stack.

## Architecture overview

```text
Browser
  │
  ▼
Angular frontend / Nginx (port 4200)
  │  /api requests
  ▼
Spring Boot backend (port 8080)
  │  JDBC + JPA
  ▼
PostgreSQL (port 5432)
```

- **Angular** is the user interface. In Docker, Nginx serves the already-built Angular files to the browser.
- **Nginx** is a web server and reverse proxy, not an Angular dependency. It serves the frontend and forwards `/api/...` requests to Spring Boot.
- **Spring Boot** does not depend on Docker-specific code. Its `application.yml` reads database connection settings from environment variables and uses JDBC/JPA to connect to PostgreSQL.
- **Docker Compose** does not create an external server. On your computer, it creates and starts the configured containers, creates a private Docker network for them, and gives each service its configured name. That is why the backend can use `database` as the database host and Nginx can use `backend` as the API host when all services run in Docker.
- **Flyway** runs when Spring Boot starts. It creates the database tables and seed applications automatically.

## Docker Compose services

Running `docker compose up --build` creates and starts these containers on the local machine:

| Compose service | Image source | Responsibility |
| --- | --- | --- |
| `database` | `postgres:16-alpine` | Stores applications and release-note entries in PostgreSQL. |
| `backend` | Built from `backend/Dockerfile` | Runs the Spring Boot REST API on port `8080`. |
| `frontend` | Built from `frontend/Dockerfile` | Runs Nginx, which serves the compiled Angular site on port `4200` and forwards `/api` calls to `backend:8080`. |

Docker Compose also creates a private network so the service names `database` and `backend` work as internal hostnames, plus the named `postgres_data` volume so database data survives a container restart. Actual container names are generated by Docker Compose and can include the project folder name, but the service names above are the names used in configuration.

When using IntelliJ for Spring Boot, run only `docker compose up -d database`; only the PostgreSQL container is started in that mode.

## Quick start with Docker

Prerequisite: Docker Desktop with Compose enabled.

```bash
docker compose up --build
```

Open http://localhost:4200. The API is available at http://localhost:8080.

This starts **all three services** (PostgreSQL, backend, and frontend). Do not start the backend from IntelliJ at the same time, because both would use port `8080`.

To stop the stack, press `Ctrl+C`. To remove the local PostgreSQL data as well:

```bash
docker compose down -v
```

## Run the backend from IntelliJ IDEA with PostgreSQL in Docker

Use this option when you want to debug the Spring Boot backend in IntelliJ while keeping PostgreSQL in Docker.

1. Start Docker Desktop.
2. From the project root, start **only** PostgreSQL:

   ```bash
   docker compose up -d database
   ```

   Docker creates the database and role automatically using these local-development values:

   | Setting | Value |
   | --- | --- |
   | Host | `localhost` |
   | Port | `5432` |
   | Database | `release_notes` |
   | Username | `release_notes` |
   | Password | `release_notes` |

3. In IntelliJ IDEA, open `backend/pom.xml` as a Maven project. Set the Project SDK to Java 17 or newer and wait for Maven import to finish.
4. Select the preconfigured **Release Notes API** run configuration in the top-right run-configuration list, then click Run.

   The shared configuration is stored in `backend/.run/Release Notes API.run.xml`. It launches `com.ayesa.releasenotes.ReleaseNotesApplication` with the default PostgreSQL environment settings.

5. On the first startup, Flyway automatically creates the tables and inserts the three selectable applications. No manual SQL or manual database creation is needed.
6. Confirm the API is running at http://localhost:8080/api/applications.

To run the Angular UI locally against that IntelliJ backend:

```bash
cd frontend
npm install
npm start
```

Open http://localhost:4200. The Angular development proxy forwards `/api` calls to the backend at `localhost:8080`.

## API routing: development versus Docker

The Angular source code calls the API through the relative path `/api`, rather than hard-coding `http://localhost:8080`. Exactly **one** of the following proxy configurations is active at a time:

| How the frontend runs | Proxy file in use | `/api` destination |
| --- | --- | --- |
| `npm start` during local development | `frontend/proxy.conf.json` | `http://localhost:8080` |
| Frontend container from `docker compose up --build` | `frontend/nginx/default.conf` | `http://backend:8080` |

The Angular development server reads `proxy.conf.json`. Nginx is not running in that mode. Conversely, the Docker image serves the compiled Angular files through Nginx, so `proxy.conf.json` is not used there.

This approach keeps frontend code independent of a machine-specific hostname, avoids browser cross-origin calls in both modes, and lets the same Angular build work both locally and inside the Docker network. Backend CORS remains configurable through `CORS_ALLOWED_ORIGINS` for direct API consumers.

## Why CORS is configured in Spring Boot

An origin includes the protocol, hostname, and port. Therefore `http://localhost:4200` (the frontend) and `http://localhost:8080` (the API) are different browser origins.

The two proxies normally avoid that browser-level cross-origin request: the browser calls `/api` on port `4200`, then Angular's development server or Nginx forwards the request server-side. CORS is still configured in Spring Boot for cases where a browser or another client calls the API directly on port `8080`.

`CORS_ALLOWED_ORIGINS` defaults to `http://localhost:4200` and can be overridden by environment variable for another deployment. It is deliberately not `*`. CORS controls which browser origins may read API responses; it is not authentication or authorization.

## Local development

Prerequisites:

- Java 17 or newer and Maven 3.9 or newer
- Node.js 20 or newer and npm
- PostgreSQL 16 (or another supported recent PostgreSQL version)

Create a local database and set its connection values through environment variables. Defaults are shown below:

```bash
# PowerShell
$env:DB_HOST = 'localhost'
$env:DB_PORT = '5432'
$env:DB_NAME = 'release_notes'
$env:DB_USERNAME = 'release_notes'
$env:DB_PASSWORD = 'release_notes'
```

Start the backend (Flyway creates the schema and seed applications automatically):

```bash
cd backend
mvn spring-boot:run
```

In a second terminal, start the UI. Its development proxy forwards `/api` to `http://localhost:8080`.

```bash
cd frontend
npm install
npm start
```

Then open http://localhost:4200.

## Configuration

The backend is configured entirely through environment variables:

| Variable | Default | Purpose |
| --- | --- | --- |
| `DB_HOST` | `localhost` | PostgreSQL host |
| `DB_PORT` | `5432` | PostgreSQL port |
| `DB_NAME` | `release_notes` | Database name |
| `DB_USERNAME` | `release_notes` | Database user |
| `DB_PASSWORD` | `release_notes` | Database password |
| `SERVER_PORT` | `8080` | API listening port |
| `CORS_ALLOWED_ORIGINS` | `http://localhost:4200` | Comma-separated permitted browser origins |

## API

| Method | Endpoint | Description |
| --- | --- | --- |
| `GET` | `/api/applications` | List available applications |
| `GET` | `/api/items` | List release-note entries, newest first |
| `POST` | `/api/items` | Create a new draft |
| `PATCH` | `/api/items/{id}/status` | Update an entry status |

Example request bodies:

```json
// POST /api/items
{
  "applicationId": 1,
  "title": "Faster customer search",
  "description": "Search results now appear with lower latency."
}
```

```json
// PATCH /api/items/1/status
{ "status": "REVIEW" }
```

## Optional enhancements delivered

- **Flyway migrations:** versioned schema creation and seed data for the selectable applications.
- **Automated tests:** three backend integration tests cover seeded data, the create-and-publish flow, and validation errors.
- **Containerisation:** separate backend and frontend Dockerfiles, plus Docker Compose for the full application and PostgreSQL.
- **Production-minded safeguards:** request validation, database constraints, structured errors, environment-based configuration, restricted CORS, and a PostgreSQL health check.

## Intentionally outside the timebox

- CI, JWT/Basic Auth, and full dev/prod profile separation were not implemented.
- The next production priorities would be OIDC/JWT with publish authorization, audit history, pagination/filtering, API contract tests, accessibility testing, and CI.

## Architecture decisions and trade-offs

- The API uses DTOs rather than serializing JPA entities, which makes the public contract deliberate and protects persistence internals.
- Applications are seeded by Flyway because the scope only needs to select existing applications; application management is intentionally out of scope.
- Status updates permit any of the three requested states. A production workflow may add role-dependent transitions and an audit trail.
- The UI has no authentication because it is optional in the assignment; the follow-up priorities are listed above.
